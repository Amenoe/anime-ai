# anime-ai 检索质量评估（M3）

纯检索的离线评估，**不在服务路径上**。

## 为什么单独做

M2 就把「检索」和「生成」拆成了两个接口（`/internal/retrieve` 与 `/internal/ai/chat`），
这个评估脚本**只打前者**，因此：

- 不依赖 LLM 生成质量，也不为评估烧对话模型的 token
- 结果可复现：同一份语料 + 同一份 golden set 必然得到同样的数字

**刻意不引入 ragas**：它面向「有 LLM 生成」的评估（忠实度、相关性等），
对纯检索的 Hit Rate / MRR 是多余依赖。自己算更快也更透明。

## 用法

```bash
# 前置：Qdrant 已导入语料，anime-ai 已启动且配了 embedding key
docker compose -f docker-compose.rag.yml up -d
mvn spring-boot:run

python3 eval/run_eval.py                       # 默认 topK=10
python3 eval/run_eval.py --topk 5              # 换 k
python3 eval/run_eval.py --json eval/out.json  # 落盘，便于两次运行对照
```

脚本**不因召回不全而返回非零**：它输出的是「测量结果」而不是「断言」，
召回率低是要改进的基线数据，不是脚本失败。

## 另外两个脚本

```bash
python3 eval/verify_ingest.py       # 验收③幂等 + ④增量（9 条断言，用虚构 id，自清理）
python3 eval/measure_import.py      # 验收⑤冷启动吞吐（抽样真实语料，自清理）
```

`verify_ingest.py` 用虚构 `subjectId`（默认 990001 起）直接传 `documents`，
所以能**精确控制内容变化**：同样的内容重导 → `upserted=0`（幂等）；
只改其中一条 → `upserted=1`（增量，且另一条不动）。
这两个数字是唯一能区分「真的重算了向量」与「全部跳过」的信号，
而只跑一次导入是证明不了的。

`measure_import.py` 用**虚构 id + 真实语料文本**测吞吐：若用真实 id 传回同样文本，
内容 hash 未变会被跳过，**测不到任何 embedding 耗时**——会让冷启动测量悄悄变成测了个空。

## M2 验收标准达成情况

| 标准 | 结果 |
| --- | --- |
| ① ≥3000 条 + payload 索引 | ✅ 3000 点，`status=green`，1024 维 Cosine |
| ② 查询结果合理 | ✅ 12 条 golden set：Hit Rate@10 = **91.7%**，MRR = **0.6285** |
| ③ 幂等 | ✅ 重复导入 `upserted=0`（`verify_ingest.py`） |
| ④ 增量 | ✅ 改一条只更新该条 `upserted=1`（`verify_ingest.py`） |
| ⑤ 冷启动耗时与花费 | ✅ 实测 300 条 / 161650 字 / **3.2s**（11ms/条），外推 3000 条 ≈ 0.5 分钟 |

> ⑤ 的耗时数字取决于 SiliconFlow 当时速度与网络，换时间跑会有出入；
> 花费见 `docs/ai-rag-practice-roadmap.md` §3.6② 的 token 估算（按字符规模核对过）。

## 两条方法论教训（比数字本身更重要）

**① `expect` 必须按「作品实际内容是否符合查询」判定，不能一条只写一个目标。**
第一版每条只写 1 个期望 id，于是把「语义正确但不是我想的那一部」判成失败：
「动画制作 职场 励志」的 top1 是《动画制作进行 黑美》——它本来就完全符合。
基线因此被系统性低估到 66.7%。补齐合理答案后是 91.7%。
反过来说，**把 `expect` 扩到 top10 全算对等于自证**，所以边缘相关的仍不收
（C2 刻意保持严格单目标，因为「家族」是它的核心限定词）。

**② 已知失败项的根因要用对照实验定位，不要停在「召回失败」这个现象上。**
唯一真失败是 `C2 催泪 家族 治愈` → CLANNAD 系列未进 top10。对照实验：

| 查询 | CLANNAD AS |
| --- | --- |
| `催泪 家族 治愈` | ❌ 不在 top5（top 全是家族题材：亚当斯一家、姆明一族） |
| `催泪 亲情 治愈` | ❌ 不在（「亲情」**在** CLANNAD 的 tags 里，仍未命中） |
| `催泪 家庭 治愈` | ❌ 不在（「家庭」在简介里） |
| `催泪 治愈` | ✅ **rank=5** |

所以**不是「语料缺词」**（换成确实存在的近义词也没用），而是
**多词查询被「强特征词」主导**：加了「家族」之后，检索被拉向家族题材，
压倒了「催泪 治愈」的信号；去掉它，目标立刻回来。

## 检索策略对照实验（2026-10-22）

策略做成了**请求参数**（`--strategy vector|hybrid|rrf|hybrid-rrf`），所以能在同一份语料上
一次跑完对比，不必改代码逐次重启。

| 策略 | Hit Rate@10 | MRR | concept | filter MRR |
| --- | --- | --- | --- | --- |
| `vector`（原状） | 91.7% | 0.6285 | 5/6 · 0.4931 | 0.2917 |
| **`hybrid`（标签加分，现默认）** | **100%** | **0.8056** | 6/6 · 0.8056 | 0.4167 |
| `rrf`（查询分解 + RRF） | 75.0% ↓ | 0.5397 ↓ | 4/6 · 0.4405 | 0.1667 ↓ |
| `hybrid-rrf` | 100% | 0.7341 | 6/6 · 0.6349 | 0.5000 |

`hybrid` 的逐条改善：C1「赛博朋克 义体 公安」rank 8→3、C2「催泪 家族 治愈」
未命中→rank 1、F2「政治 阴谋 机甲」rank 4→2。做法是先多召回 3 倍候选，再按查询词
命中 `name`/`tags`/`meta_tags` 加分重排（上限 0.08）。只拼标签不拼简介——简介命中
几乎恒真，加分就失去区分度。

### 两个反直觉的负结果（比正结果更值得记）

**① 查询分解 + RRF 比不做还差**（91.7% → 75.0%）。原本的判断是「多词查询被强特征词
主导」（这个诊断是对的：去掉「家族」只用「催泪 治愈」，CLANNAD 立刻回到 rank 5），
但「让每个词都发声」这个药方是错的 —— RRF 只吃排名、丢掉相似度，等于给每个子查询
**同等投票权**；而「家族」这一路本身就是低质量召回（top10 全是家族题材噪音），
融合时这些噪音被抬到前面，真正的目标反被稀释。

**② 语料「去噪」让 MRR 明显下降**（hybrid 0.8056 → 0.6974）。去掉 tags 里的年份噪声
（占 9.4%）并给 `meta_tags` 去重（6.1% 的条目有重复项，如攻壳 S.A.C. 每个标签重复两次），
看起来是修数据质量问题，实测却更差，filter MRR 尤其从 0.4167 掉回 0.2917。
原因是**重复其实意外起了词权重加倍的作用**，强化了「科幻」「战斗」这类题材词；
去重把权重抹平，题材类召回随之变弱。已回滚（并用 Qdrant 快照恢复，未重新 embedding）。

⚠️ 由此得出一条可复用的判断：**「看起来是 bug 的数据特征」不一定该修**，它可能在
补偿别处的不足。这类改动必须先对照测量再定。

## 冷启动耗时的真实数字

之前 `measure_import.py` 外推「3000 条约 0.5 分钟」是**错的**：它只测了 embedding，
没算 Bangumi 分页拉取（30 页 × 1 秒间隔 + 每页请求时间）。2026-10-22 实测
`{"source":"bangumi","limit":3000}` **约 3 分 42 秒**（`upserted=3000`，全部重算）。
以后引用这个数字请用实测值。

## 下一步（尚未做，按性价比排序）

1. **主动加权题材词**：既然「重复 meta_tags 意外有效」，那就**显式**重复
   `meta_tags`（如 2~3 次）做手工 term weighting，看能否超过 0.8056。这是负结果
   直接指向的下一步，成本低（改一行 + 重导 3.7 分钟）。
2. **`filter` 类 MRR 仍是弱项**（0.4167）：`hybrid-rrf` 在这项上更高（0.5000），
   但总体 MRR 更低。可以考虑只对「题材组合」类查询启用不同的混合权重。
3. golden set 需要扩充（当前 12 条，C2/S1 这类单点样本对结论影响偏大）。
